## New findings

### F1 (P0): `GET /state` does not return the stored snapshot → user progress is lost on re-login ❌

This is the most important finding of this session. The round-trip is broken:

- `PUT /state` (`users/routes.ts:92–145`) stores the client's full `PersistedSnapshot`
  (progress, quizAttempts, challengeAttempts, projects, currentCircuit, settings,
  activity, tutorHistory) in `user_snapshots`.
- `GET /state` (`users/routes.ts:24–90`) **never reads `user_snapshots`**. It returns
  `{ user, activities, circuits, xp, streak, achievements, levelInfo, recentXp }`.
- The frontend consumes GET on sign-in: `StoreProvider.tsx:402–404` →
  `dispatch({ type: 'state/hydrate', persisted: remoteState })` →
  `applySnapshot` (`src/state/persistence.ts:70–126`) reads
  `progress`, `quizAttempts`, `challengeAttempts`, `achievements`, `projects`,
  `currentCircuit`, `settings`, `activity`, `tutorHistory` — **none of which GET sends**.

Net effect: lesson progress, saved circuits, quiz attempts and tutor history are wiped
from the UI on every re-login. This is exactly Bug 2 that `bug-reproduction.test.ts`
guards against at the DB level — but the test only checks a *new* user sees no state;
it never asserts the same user gets their own snapshot back. The end-to-end path is
untested and broken.

**Fix (small, backend-only):** in `GET /state`, load the stored snapshot and merge:

```ts
const row = await db.get('SELECT snapshot FROM user_snapshots WHERE user_id = ?', user.id);
const snapshot = row ? JSON.parse(row.snapshot) : null;
res.json({
  ...(snapshot ?? {}),
  user: { id, email, name, level },   // server values win
  xp, streak, levelInfo, recentXp,    // server-authoritative (audit-1 §2.2)
  achievements: snapshot?.achievements ?? [],  // see F2 — must be string[]
});
```

Server-computed fields should override the snapshot (the snapshot's user.xp is
client-computed and may drift; server xp_ledger is the source of truth).

### F2 (P1): `achievements` type clash between backend and frontend contract ❌

- Backend GET /state sends `achievements` as **objects**:
  `{ id, name, description, xpBonus, unlockedAt }[]` (`users/routes.ts:77`,
  `rewards/index.ts` `getUserProgress`).
- Frontend `PersistedSnapshot.achievements` is **`string[]`** (achievement ids —
  `src/state/types.ts`; consumed as `state.achievements.includes(id)` in
  `reducer.ts:65`, `Dashboard.tsx:269`).

After the F1 fix, hydrating object[] into `achievements.includes(...)` breaks. The fix
must keep BOTH consumers: `achievements: string[]` (ids, for hydrate) — and, if we want
the UI to show metadata later, expose the detailed objects under a separate key
(`achievementDetails`). Do not overload one key with two shapes.

### F3 (P1): No challenge submission endpoint → challenges never award server-side XP ❌

Spec §3 / plan B2 requires XP on challenge pass. Reality:

- `challenges/routes.ts` is GET-only (list + detail).
- No `INSERT INTO challenge_attempts` anywhere in `backend/src` (verified by search).
- The client computes passes locally (`reducer.ts:341–347` awards client-side XP) and
  merely PUTs the resulting `challengeAttempts` array inside the snapshot. The server
  neither validates nor records nor pays for it. `state.test.ts` even PUTs a
  `challengeAttempts` array that nothing ever reads.

**Honest implementation (B2 closure):** add `POST /api/challenges/:id/submit` that
takes the submitted circuit, runs it through the real simulator, evaluates the
challenge's checks **server-side** (the seeded challenge definitions with their check
predicates already exist in `backend/src/data/challenges.ts` — the backend tree mirrors
the frontend), records `challenge_attempts`, and calls `awardXp(sourceType:
'challenge_passed', sourceId: challengeId)` on pass. Do NOT trust a client-sent
`passed: true` boolean — that is fake validation. Frontend wiring (calling this
endpoint from the reducer flow) is a minimal `services/api.ts` change and can land with
C5; the endpoint itself belongs in Phase B.

### F4 (P1): UNIQUE index missing on pre-existing databases ⚠️

The duplicate-XP fix puts `UNIQUE (user_id, source_type, source_id)` inside
`CREATE TABLE IF NOT EXISTS xp_ledger` (`db/index.ts:189–210`). That helps fresh DBs
only. Any database created before this change (including the tracked
`data/qubitverse.db`) keeps the old constraint-free table — `CREATE TABLE IF NOT
EXISTS` is a no-op there, and `migrateDatabase` (`db/index.ts:44–66`) doesn't add the
index. Duplicates are still possible on existing data.

**Fix:** after the `xp_ledger` CREATE TABLE in `initializeDatabase`, add
`CREATE UNIQUE INDEX IF NOT EXISTS idx_xp_ledger_unique ON xp_ledger(user_id,
source_type, source_id)`. Caveat: if the existing table already holds duplicate
rows, index creation fails — clean duplicates first (keep the latest by `created_at`),
then create the index. While in `migrateDatabase`, delete the dead empty
`if (!userColNames.includes('xp')) {}` block (`db/index.ts:57–60`).
