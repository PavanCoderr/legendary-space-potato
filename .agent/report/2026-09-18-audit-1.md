## 1. A5 verification detail (logout/revocation)

Correct pieces:
- Sessions written at signup AND login with `jti` = uuid, 24h `expires_at` (`auth/routes.ts:47-56, 89-98`).
- JWT payload carries `jti` (`utils/jwt.ts`); middleware checks the session row exists and is unexpired (`middleware/auth.ts:27-49`).
- Logout deletes ONLY the current session (`DELETE FROM sessions WHERE id = ? payload.jti`) — other devices keep working. Matches the plan exactly.

Notes (not blockers):
1. **Fragile rejection path**: on revoked/expired sessions the middleware calls bare `next()` without setting `req.user`. Protection works only because every route happens to do its own `getUser()` + 401. One future route forgetting that check = silent auth bypass for revoked tokens. Recommend: `api.use(..., authenticate, requireAuth, ...)` in `routes.ts` so rejection is centralized. (Also the catch-block fallback "DB error → token-only auth" means a DB outage accepts revoked tokens — acceptable, but document it.)
2. `signToken` passes jti via payload rather than the `jwtid` option — the comment's claim that both together error is plausible; payload-jti is fine since verification reads the payload.

## 2. Phase B — real issues found ❌

### 2.1 Duplicate-XP hole (spec §3 hard requirement)
Plan required `UNIQUE(user_id, source_type, source_id)` on `xp_ledger` + idempotent insert. Reality:
- `xp_ledger` (`db/index.ts:196-206`) has **no UNIQUE constraint** — PK is a fresh uuid per insert.
- `awardXp` (`rewards/index.ts:146-200`) blind-INSERTs every call.
- Quiz route awards on **every** correct submit with `sourceId = quizId` (`quizzes/routes.ts:160-170`) → answer the same quiz correctly twice = paid twice. **Violation.**
- Lesson route is properly guarded by the not-completed → completed transition ✅. Achievement bonuses are guarded by `user_achievements` PK ✅.

**Fix (small):** add `CREATE UNIQUE INDEX IF NOT EXISTS idx_xp_ledger_unique ON xp_ledger(user_id, source_type, source_id)`; change `awardXp`'s INSERT to check changes: use `INSERT OR IGNORE` + inspect `changes` (or SELECT-before-INSERT inside the existing transaction); skip the `users.xp` bump when ignored. Caveat: SQLite treats NULLs as distinct in UNIQUE — fine here because quiz/lesson/challenge awards always set `source_id`.

### 2.2 B3 not wired to the frontend contract
New `GET /api/achievements/progress` returns xp/streak/achievements — but the frontend's state flow consumes `GET /state` (`loadState`), and `users/routes.ts` **contains no xp/streak/achievements**. Server-side XP exists but never reaches the existing UI. B3 acceptance (per plan: expose via `/state` matching frontend contract) is unmet. Merge `getUserProgress`'s data into the `/state` GET response.

### 2.3 Streak edge-case bug (new finding)
`updateStreak` only UPDATEs the `activities` row. A user whose first action is a quiz (before ever hitting `/state`) has no `activities` row → UPDATE affects 0 rows → active days silently not recorded until the first `/state` GET. Fix: `INSERT OR IGNORE INTO activities (user_id) VALUES (?)` at the top of `updateStreak`.

### 2.4 Minor
- `dayKey()` uses server **local** time, plan said UTC. Single-server OK; set container TZ=UTC or switch to UTC in the util.
- Backend now has its own copies of achievements (`rewards/index.ts`) and glossary (`data/glossary.ts`) — currently **in sync** with frontend (verified ids, xpBonus, level formula identical) but there is no drift test. Extend E3 to cover achievements + glossary.
